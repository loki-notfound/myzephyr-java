14. Building and verifying

Every zephyr-java release is built from pinned sources with scripts in this repository, and every release can be rebuilt and compared. This chapter describes the pins, the root certificates, the build-layer patches, the builds, the manifest and the signatures. It ends with how to reproduce a release and how the guide's site is built.

The pins#

bin/pins.env names the two source trees of the native core, by commit, from the zephyr-backports release set of 2026-11-07:

TreeRepositoryTagCommit
zephyrzephyr-backports/zephyrv2.3.0-sec.28c6a120256b4bd887d6e7167d929d76e3507e0e5
zephyr-cppzephyr-backports/zephyr-cppv2.3.0-sec.13a2ee602ee28e6b7941b617ad4706349ad992641

The backports number each fork on its own, so the two tags differ. A release set says which tags belong together. This one also names zephyr-javascript and zephyr-wallet v2.3.0-sec.1, which zephyr-java does not build. The release version's sec.<N> is zephyr's number.

zephyr-cpp is the git submodule external/zephyr-cpp, at that commit. The zephyr tree is placed by bin/place_zephyr_tree.sh, which the build scripts call, at external/zephyr-cpp/external/zephyr, fetched by commit. zephyr-cpp's own bin/update_submodules.sh is never used, because it checks out a branch. Nothing is ever built from a branch. When a tree's own tag (ZEPHYR_TAG, ZEPHYR_CPP_TAG) is present locally, the scripts check that it points at the pinned commit. They also run git verify-tag on it (Signatures).

The backports are ZephyrProtocol's Zephyr 2.3.0 plus Monero security fixes, with no changes to the headers that zephyr-java compiles against. A build against ZephyrProtocol's original release must therefore work too: zephyr tag v2.3.0 (67c5f53b878fef41fb5e74c4382d5b7a2f37fd8a) and zephyr-cpp 4a99272f6d7a171cf6625016939094637459975a (zephyr-cpp has no tag there). The comments in bin/pins.env name both. To build against them, put their URLs and commits into the four variables and check out the submodule at that commit. This is a requirement on the sources, not a CI job; releases are always built from the backports.

The root certificates#

The library ships Mozilla's root certificates as curl publishes them (src/main/resources-raw/zephyr/common/cacert.pem, the default trust of the native wallet on Android). They are a pinned input like the sources:

  • bin/ca-bundle.env names the dated file by date, URL and sha256;
  • bin/update_ca_bundle.sh downloads it and checks the hash;
  • bin/check_versions.sh, the first step of every release build, fails when the committed file differs from the pin.

Builds never download it. Before each release bin/update_ca_bundle.sh --check-latest says whether curl has published a newer file; the release then moves the pin to it.

Build-layer patches#

zephyr-java never patches zephyr or zephyr-cpp source code. It does patch build tooling: six patches under patches/depends/, each with a DEP-3 header. The build scripts apply them to zephyr's contrib/depends, the tree that builds boost, OpenSSL, unbound and the other libraries from pinned archives. One of them, 0006, adds a patch that the OpenSSL recipe applies to OpenSSL's own source:

PatchWhatWhy
0001-android-ndk-python3run NDK r18b's toolchain script with python3current hosts have no Python 2
0002-boost-1.64-b2-engine-declarationsadd the includes and two prototypes boost 1.64's build engine needsgcc 14 rejects implicit declarations
0003-android-ndk-x86_64pass --arch x86_64 for the x86_64 standalone toolchainthe x86_64 Android toolchain is not built otherwise
0004-openssl-openssldirbuild OpenSSL with OPENSSLDIR /etc/sslthe default embedded the build directory, an empty CA store on any other machine
0005-neutral-engines-and-unbound-sysconfdirneutral ENGINESDIR, MODULESDIR and unbound sysconfdirthey embedded the build directory, which breaks reproducibility across paths
0006-openssl-android-environmenton Android, OpenSSL's OPENSSL_issetugid() compares the user and group ids instead of asking getauxval(AT_SECURE)AT_SECURE is set in every Android app process, so OpenSSL ignored SSL_CERT_FILE and SSL_CERT_DIR there and the native wallet could not verify an https:// node

Three more build-layer settings:

  • zephyr is configured with USE_DEVICE_TREZOR=OFF, and depends leaves out protobuf and its compiler protoc. The Java API cannot reach a hardware device, so the Trezor code and protobuf are not linked; zephyr builds its device_trezor library as the stub it provides for that case. On Linux, hidapi with libusb and eudev is still built and linked, because zephyr's device library compiles its Ledger code when hidapi is available. ZephyrProtocol's original v2.3.0 has the same CMake and depends files for this, so the setting applies there unchanged;
  • the JNI library is compiled with -include map, because zephyr-cpp's model header relies on boost to include <map> and newer boost does not;
  • zephyr's dead blocks library is not linked, because the pinned tree never builds it.

The builds#

Clone and fetch the submodule (not recursively; the scripts place the zephyr tree themselves):

Shell
git clone https://github.com/loki-notfound/myzephyr-java.git
cd myzephyr-java
git submodule update --init external/zephyr-cpp

There are four entry points:

  • bin/build_libzephyr_java.sh, the developer build. It builds zephyr and the JNI library against the host's shared libraries (boost, OpenSSL, unbound, sodium, hidapi) into build/, where mvn test finds it. Quick, but the result runs only on hosts like the one that built it. The CI workflow's "System libraries of the developer build" step lists the packages it needs on Ubuntu 24.04.
  • bin/build_linux_container.sh <x86_64|arm64|--all>, the Linux release natives. It runs bin/build_linux.sh in the pinned debian:12 image with podman or docker, the same image as the CI job. Everything but glibc comes from zephyr's depends and is linked statically. The results are build/natives/linux-<arch>/libzephyr-java.so.
  • bin/build_android.sh <abi|--all>, the Android natives with zephyr's depends and NDK r18b (downloaded and checked by depends), into build/android/<abi>/. For releases, bin/build_android_container.sh <abi|--all> runs it in the same pinned image.
  • bin/build_release.sh, everything: the natives, stripping with separate debug files, the JAR with sources and Javadoc jars, the AAR through Gradle in android/, and dist/<version>/ with manifest.json and SHA256SUMS. The pure tests run on the depends-built library. It also writes dist/<version>/central/, the Maven Central bundle before signing (Maven Central).

The packaging of bin/build_release.sh runs in the same pinned image (bin/package_release_container.sh, with the image's own JDK and Maven). It needs podman or docker and an Android SDK in ANDROID_HOME, which it mounts read-only. The SDK needs cmdline-tools 22.0, platforms;android-36 and build-tools 36.0.0. BUILD_LINUX_ARCHES and BUILD_ANDROID_ABIS choose what to build; an empty value builds none. SKIP_NATIVES=1 packages the natives already in build/ again.

Every step is a plain shell command, so the same scripts serve a developer, CI and an F-Droid build. The first depends build takes a while: about 14 min per Android ABI and 10 min for Linux x86_64 on the machine this project is developed on. Depends downloads each source archive from the address in its recipe. When that fails or stalls (below 1000 bytes/s for 2 min), it uses downloads.getmonero.org. Either way it checks the archive's sha256 against the recipe before it uses it.

Reproducibility#

Two builds from the same commit give the same files:

  • SOURCE_DATE_EPOCH is the commit time unless set, and goes into every step; Maven gets it as project.build.outputTimestamp.
  • The Linux natives are built with gcc and -ffile-prefix-map, so they contain no build path and are the same from any checkout directory. Verified: the x86_64 library and its debug file were equal across two checkout paths.
  • The Android natives are reproducible at the same build path only. NDK r18b's clang 7 cannot rewrite __FILE__, so about 700 source paths per library keep the build directory: source file names in error messages, and the location of lambdas in function names. They leak nothing beyond that directory name. Release builds therefore run at a fixed path, as F-Droid does. Verified: arm64-v8a was equal on a rebuild at the same path.
  • The JARs and the AAR were equal across clean builds. Stripping is deterministic, and the debug symbols are packed into a tar with fixed order, times and owners.

The manifest#

dist/<version>/manifest.json records what went into a release:

KeyContents
corezephyr and zephyr-cpp: repository URL, tag, commit; release_set (the zephyr-backports release set, 2026-11-07) and release_set_members (name, tag, commit of each member)
dependsevery package of zephyr's depends: archive name, version, sha256
patchesthe build-layer patches: name, sha256
root_certificatesthe shipped root certificates: date, URL and sha256 of curl's dated file
toolchaingcc, binutils, CMake, glibc, JDK and Maven of the packaging environment (packaging_env, packaging_container), NDK (version and sha256) and its clang, Android Gradle plugin, Gradle (distribution and sha256), compile and min SDK, build-tools, the Android SDK package revisions; per Linux native its compiler, glibc and container; per Android native its NDK, clang, API level, build path and container
zephyr_javathe commit, its SOURCE_DATE_EPOCH, the version
artifactsevery release file with its size and sha256
central_bundleevery file of the Maven Central bundle (checksum files aside) by its repository path, with its size and sha256

SHA256SUMS lists every file of the release, the manifest included. The site is the archive site-<version>.tar.gz, whose hash is in SHA256SUMS; Pages serves its contents.

Maven Central#

The releases are published on Maven Central under dev.lateo, from 2.3.0-sec.2-java.5 on. The release build writes the bundle for it, dist/<version>/central/ (bin/make_central_bundle.sh). It holds both artifacts in Maven repository layout (dev/lateo/zephyr-java/<version>/, dev/lateo/zephyr-java-android/<version>/). Each comes with its sources jar, Javadoc jar and POM, the AAR also with its Gradle module metadata. An .md5, .sha1, .sha256 and .sha512 lie next to every file. Every file is a release file byte for byte, except the AAR's Javadoc jar, which is the JAR's under the AAR's name: both compile the same sources. The script refuses a -SNAPSHOT version and a POM without the fields Central requires (name, description, url, licence, developer, scm). Both POMs name two licences: the MIT licence of the library, and the Mozilla Public License 2.0 of the shipped root certificates (cacert.pem).

The bundle is not a release asset; manifest.json lists its files. The maintainer signs it with bin/sign_central_bundle.sh. The script checks the checksums and refuses when the maintainer key's secret key is absent. It writes an .asc next to every file but the checksums, verifies them, and writes the zip that is uploaded to the Central Portal. --dry-run runs the checks and lists the files without signing.

Releases up to 2.3.0-sec.2-java.4 were published under io.github.loki-notfound in a Maven repository on the project's GitHub Pages. That repository is no longer served; those releases remain as GitHub releases with their signed SHA256SUMS. A build that still resolves one of them from that repository stops resolving, whether it upgrades or not. There are two ways out:

  • move to dev.lateo:zephyr-java:2.3.0-sec.2-java.5 or dev.lateo:zephyr-java-android:2.3.0-sec.2-java.5 from Maven Central;
  • take the older release's JAR or AAR from its GitHub release and check it against that release's SHA256SUMS. Use it as a file dependency, and add its three runtime dependencies: com.fasterxml.jackson.core:jackson-core and com.fasterxml.jackson.core:jackson-databind 2.13.5, and org.apache.httpcomponents.client5:httpclient5 5.2.1.

Signatures#

Two keys are involved:

  • The maintainer key 31DA 39AB 43E0 CA67 F1F3 A661 BA2A FF22 DF8A 4A13 signs the zephyr-java release tags, SHA256SUMS and every file on Maven Central (its .asc). It is KEYS.asc in this repository.
  • The zephyr-backports release key FB39 94F0 997C A6F0 43D7 2491 9EFF 03F5 27D2 40A1 signs the core's tags. It is keys/zephyr-backports.asc in the zephyr-backports repository. The build scripts verify the tags with git verify-tag when the tag is present. Without gpg or without the key they print a warning and build anyway; a bad signature stops the build.

To check a release you downloaded:

Shell
gpg --import KEYS.asc
git verify-tag v2.3.0-sec.2-java.5
gpg --verify SHA256SUMS.asc SHA256SUMS
sha256sum -c SHA256SUMS

Run git verify-tag in a clone of this repository, and the last two commands in the directory of the release files. Then compare core in manifest.json with bin/pins.env at the tag. A file from Maven Central is checked against its .asc the same way, for example gpg --verify zephyr-java-<version>.jar.asc zephyr-java-<version>.jar. Its sha256 is in SHA256SUMS (the jars, the AAR, the POMs and the AAR's module metadata) or in manifest.json (central_bundle, for the AAR's copy of the Javadoc jar).

Reproducing a release#

The release flow:

  1. CI builds the artifacts.
  2. A second build in the same environment must give the same hashes.
  3. Only then is SHA256SUMS signed, on the maintainer's machine.

Anyone can repeat the second build. Every release file comes from one environment, in CI and locally alike: the pinned debian:12 image, the checkout at /work and umask 022. The image's packages (compilers, OpenJDK 17, Maven) come from the Debian snapshot 20261107T000000Z. The image installs them from snapshot.debian.org (recorded in the manifest as toolchain.debian_snapshot), so both builds use the same compilers and binutils. The source paths that NDK r18b leaves in the Android libraries read /work/... on both sides, and the libraries match.

The natives are built in that image, and so is the packaging. CI's package job runs bin/package_release.sh in it; locally bin/package_release_container.sh does the same with the Android SDK mounted read-only. The jar entries and the tar archives carry normalised modes (-rw-r--r--, -rwxr-xr-x for the natives, drwxr-xr-x). So the jars, the AAR and the archives of the two builds can match byte for byte, not only the natives. The Javadoc is generated from a sorted list of the source files (bin/javadoc_sorted.sh). JDK 17's javadoc builds its index in the order it reads the files, which would otherwise be the file system's.

The whole second build is two commands:

Shell
git submodule update --init external/zephyr-cpp
ANDROID_HOME=<android-sdk> bin/build_release.sh

Replace <android-sdk> with the directory of your Android SDK. dist/<version>/SHA256SUMS can then be compared with the release's. Step by step:

  1. Clone, check out the release tag, verify it, and fetch the submodule (The builds, Signatures).
  2. Build the Linux natives with bin/build_linux_container.sh --all and compare each build/natives/linux-<arch>/libzephyr-java.so with the copy inside the release JAR (unzip -p zephyr-java-<version>.jar linux-x86_64/libzephyr-java.so | sha256sum).
  3. Build the Android natives with bin/build_android_container.sh --all, and compare with the libraries in the AAR (jni/<abi>/libzephyr-java.so).
  4. Package with bin/package_release_container.sh <version> and compare the jars, the AAR and the archives with the release's. manifest.json itself records the build environment (compilers, glibc, JDK, Maven, the SDK packages, the container). Its hash matches only a build in the same environment.

The stripped libraries carry a gnu_debuglink to their debug files, which ship in debug-symbols-<version>.tar.gz. A crash report from a release can therefore be symbolised without rebuilding.

The guide and its site#

This guide is the Markdown in docs/guide/, readable on GitHub as it is. It is also a static site on the project's GitHub Pages, https://java-docs.lateo.dev/guide/. Two scripts build and check it, with Python 3 and its standard library only:

Shell
bin/build_site.sh
bin/check_site.sh

bin/build_site.sh writes the landing page, one page per guide file, the assets and the CNAME file with the site's domain to build/site/ (site/build_site.py). Its Markdown converter (site/markdown.py) knows exactly the Markdown this guide uses and fails on anything else, so a page never differs from what GitHub shows.

bin/check_site.sh checks the result (site/check_site.py):

  • a page for every guide file;
  • the page policy default-src 'none'; style-src 'self'; img-src 'self'; base-uri 'none'; form-action 'none' in every page;
  • no script, no style attribute, no external resource or absolute path;
  • well-formed pages;
  • every relative link and anchor resolves;
  • CNAME holds java-docs.lateo.dev, and there is no maven/.

The pages carry no JavaScript. The footer names the version and the commit with its date, so the same commit gives the same site.

Two forms go beyond plain Markdown:

  • Callouts. A callout is written in GitHub's alert syntax: a block quote whose first line is > [!NOTE], > [!WARNING] or > [!CAUTION], and whose next line starts with a bold title. It becomes an info, warning or danger box on the site, at most two per page. Any other block quote is an error.
  • Compiled examples. A Java block whose info string names a compiled example, java examples/<Class>.java, is labelled "Java, compiled". The file must exist in src/test/java/examples/. The pure tests (TestExamples) check that the block is verbatim in it.

The version a release names in the guide and in the README is checked as well. bin/check_versions.sh fails when a coordinate, the Maven snippet, the version catalog entry, a git verify-tag line or the index's version line names another version than pom.xml.

bin/make_site.sh builds the same pages into a release's site, next to the Javadoc. The site archive of a release therefore carries the guide of its commit. Every CI run builds and checks the site too (job java).

The look comes from the lateo house style, @lateo/style 0.1.0. site/assets/ holds unchanged copies of its stylesheets content.css and print.css (BSD 3-Clause, LICENSE-style.txt) and of its favicons; STYLE-VERSION names the version. site/assets/site.css is this repository's own, under its MIT licence. The lateo name and the favicons are under neither licence: site/assets/NOTICE.txt and site/assets/TRADEMARKS.txt state the terms.
