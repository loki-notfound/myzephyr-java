9. Errors and exceptions

This chapter covers what a wallet app sees when something goes wrong. It names the exception types and where their messages come from, lists the messages a wallet meets, and shows how to log them safely. It ends with the core's own log.

ZephyrError#

zephyr.common.ZephyrError is the exception the library's own checks and most wallet calls throw. It is not the only one: Calls that let the core's exception through names the others. It extends RuntimeException, so the compiler does not ask you to catch it. It carries a message and an optional Integer code:

  • getMessage() is the text;
  • getCode() is the code, or null;
  • toString() is the message, or "code: message" when there is a code.

Many wallet calls catch the native failure and throw a ZephyrError with the core's message and no code. Two calls set the code -1: getReserveProofAccount and checkReserveProof. Checks in the Java code, such as a missing network type or a closed wallet, throw a ZephyrError as well.

The JNI bridge turns a C++ exception into a java.lang.Exception (an IOException for an I/O failure, an OutOfMemoryError when memory runs out). A wallet call that wraps it catches the Exception and rethrows it as a ZephyrError; an OutOfMemoryError passes through unchanged.

Calls that let the core's exception through#

Not every call of ZephyrWalletFull wraps the core's failure. In 2.3.0-sec.2-java.4 these pass it on as java.lang.Exception (or IOException), as read in the source:

  • openWallet from a path, openWalletData, and createWallet for a random wallet or one from a mnemonic;
  • save, moveTo and getData;
  • the six balance calls (getBalance, getUnlockedBalance), getReserveInfo and getCirculatingSupply: they catch only ZephyrError, which the bridge never throws;
  • getOutputs, getHeight, getRestoreHeight and setRestoreHeight;
  • the account and subaddress calls (getAccounts, getAccount, createAccount, getSubaddresses, createSubaddress, setSubaddressLabel, getAddress);
  • getTxNotes, setTxNotes, the export and import of outputs and key images, signMessage, the address book and the attributes;
  • the getters of the keys, the mnemonic, the path and the network type.

Observed on 2026-11-17, also with the released JAR: openWallet with a wrong password threw java.lang.Exception with the message "invalid password", not a ZephyrError. In the core's code, getCirculatingSupply without a node throws "failed to get circulating supply. Make sure you are connected to a daemon." the same way. The rule that follows: catch Exception around wallet calls, not only ZephyrError (Opening wallet files).

Some of these calls do not catch the core's failure in the native code either. Among them are the account and subaddress calls and getAddress (read in the bridge's code). An exception that leaves native code uncaught can end the process. An invalid account or subaddress index is the likely trigger, so pass only indexes the wallet reported. This was not run.

A few calls have no check for a closed wallet, among them changePassword. After close() it fails with an unrelated error instead of "Wallet is closed" (read in the source).

ZephyrUtils.validateAddress turns its AssertionError into a ZephyrError; isValidAddress returns false instead of throwing.

What an app can tell apart. The type separates only the broad cases. A library check or a wrapped core failure is a ZephyrError, a core failure that was not wrapped a java.lang.Exception, and an RPC error a ZephyrRpcError. Every refusal of createTxs by the core is the same ZephyrError with a null code; only the text differs. So the message table above is the only handle, and its texts are not guaranteed to stay the same across releases of the core. As advice:

  • check what you can before you build: round a conversion to four decimals, compare the amount with the unlocked balance, read getReserveInfo();
  • match a known message only to choose a better screen text, and fall back to a general failure;
  • keep the message for the log.

In the runs of 2026-11-17 the messages of createTxs held only the core's own text. But a core message can carry text from the node. The core passes the node's own error text into some messages (read in the core's code; A remote node). Show such text as plain text, never as HTML.

Showing an error#

As advice for screens, state what happened, why if known, and what to do next. For example, for "not enough money": "This account cannot pay the amount and its fee. Enter a smaller amount, or wait for pending funds to unlock." Keep the core's message for the log.

Logging safely#

Never log ZephyrRpcError.toString().

It appends the RPC method and its parameters as JSON. The calls of ZephyrWalletRpc that open or create a wallet put the wallet's password into those parameters, and its setDaemonConnection the node's login password. Log getMessage() and getCode() instead.

Releases after 2.3.0-sec.2-java.4 print the values of password, old_password, new_password, seed, seed_offset, spendkey, viewkey and tx_key as <redacted> in toString(), while getRpcParams() still holds them.

toString() also reaches a log without an explicit call: through printStackTrace(), through "" + e, and through the throwable output of most loggers. Never log the mnemonic, the private keys or the wallet password. For a ZephyrError without a code, getMessage() and toString() are the same text.

The library logs secrets itself at some settings (read in the source):

SettingWhat is logged, and where

On Android, System.out and System.err go to logcat. In a released app, keep FINE logging of the library off and do not call setLogLevel or configureNativeLogging. Without them the core printed nothing in the runs of 2026-11-17.

The native log#

The core has its own log, separate from Java's. ZephyrUtils.setLogLevel(level) sets the level of zephyr-java's own messages (printed with System.out) and, once the native library is loaded, the core's level as well. ZephyrUtils.configureNativeLogging(path, console) sends the core's log to a file.

Observed on 2026-11-17 on the desktop:

SettingWhere the core's log goes
neither callnowhere: no line on stdout or stderr, no file, even for errors
setLogLevel(0)warnings and errors on stdout, no file
setLogLevel(1)informational lines as well, still on stdout only
configureNativeLogging(path, false)the file at path, nothing on the console; without setLogLevel at the categories of level 0
configureNativeLogging(path, true)the file, and the same lines with ANSI colour codes on stdout

Nothing went to stderr in any variant. The "no file" results rest on a search of the likely directories, not on a trace of every file the process opened.

The log holds private data. At level 0 it already records the wallet's primary address, the wallet file's path, and for each received or spent output the amount and the transaction hash. At level 1 it adds the node's URI. At level 1 the console line for an exception also carries the absolute source path of the machine that built the library. Treat a log file like the wallet: keep it in the app's private storage, out of backups and crash reports, and switch it on only to debug.

The log can grow fast. With a listener registered, a level-0 file log grew by one error line per scanned block: about 1.1 MB for 7,700 blocks. The line was "wait should have been called before waiter dtor - waiting now". Without a listener there were 4 such lines.

These runs used a developer build of the 2.3.0-sec.2-java.4 sources on Linux. A level-0 log of the released JAR held the same lines on 2026-11-17: the primary address, the wallet path, and the amounts and hashes of the outputs. Levels above 1 were not tried. On Android, configureNativeLogging has not been tried; nothing the core logs appears in logcat (Logs).
